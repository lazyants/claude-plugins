# Publish-target adapters

This directory holds one Markdown file per supported publish target. The base `SKILL.md` selects an adapter at the publish step by reading `references/publish-targets/<resolved-name>.md`, where `<resolved-name>` is the `publish.target` value in the consuming project's `.claude/handbook/profile.yml`, lowercased with underscores replaced by hyphens (see "Naming").

## Selection mechanism

At the publish step, the base skill does this (in prose, not code):

1. Read `publish.target` from the loaded profile.
2. Try to open `references/publish-targets/<resolved-name>.md`, where `<resolved-name>` is the `publish.target` value lowercased with underscores replaced by hyphens (e.g. `obsidian-vault.md` when `publish.target: obsidian_vault`, `static-md.md` when `publish.target: static_md`). See "Naming" below.
3. If the file does not exist, halt with: `"No publish-target adapter for <value>. Available: <list of files in this directory minus README.md>."` No partial output, no file writes.
4. Otherwise follow the adapter's instructions to write the chapter, wire it into the index/parent, and add glossary entries.

The base skill never branches on target name in its own prose. All target-specific knowledge lives in the adapter file. This is the only extension point.

## What ships

Two adapters ship: `obsidian-vault.md` and `static-md.md`. The latter is the universal plain-Markdown fallback — it publishes to a GitHub wiki, an MkDocs tree, a GitBook (via `SUMMARY.md`), or a plain repo. Three candidates remain unimplemented — `confluence`, `gitbook`, `docusaurus`; setting `publish.target` to any of those triggers the halt above.

## Adding a new target X

Create `<X>.md` in this directory (filename must match the `publish.target` value, kebab-cased; e.g. `publish.target: confluence` -> `confluence.md`). **Writing the file is not sufficient to make the target selectable, and this is the first thing to get wrong.** `publish.target` is a CLOSED enum in `assets/profile.schema.json`, and Step 0's schema validation runs BEFORE adapter resolution — so a profile naming your new target is rejected outright, with `value "X" not in enum [...]`, and your adapter is never reached. Add `X` to that enum in the same change, and re-run the schema evaluator against a profile that selects it before assuming the adapter works. Then model the file on `obsidian-vault.md` and document, in second-person voice, every binding the base skill needs to write a chapter through this target. Concretely, your adapter MUST cover:

- **Chapter file creation.** Where the chapter file lands relative to `publish.chapters_dir`, what extension it uses, what filename convention (slug from the manifest, kebab-case, etc.), and how to handle name collisions.
- **Index / parent wiring.** How to register the new chapter in `publish.index_file` (or the target's equivalent parent structure — a Confluence parent page id, a Docusaurus `sidebars.js` entry, a GitBook `SUMMARY.md` line). Specify exactly which file you edit and where in it.
- **Frontmatter / metadata.** Whether the target needs frontmatter at all. If `publish.frontmatter_required: true`, document the exact required keys (e.g. `title`, `language`, `audience`, tags) and how their values are derived from the profile and the manifest entry. If the target uses a different metadata mechanism (Confluence labels, Docusaurus `id`/`sidebar_position`), document that instead.
- **Glossary entries.** How to write glossary entries to `publish.glossary_dir`: one file per term vs. a single combined file, naming convention, cross-link format, and how to seed from `publish.glossary_seed` — which is OPTIONAL: reconcile against it only when the key is set and readable, never make a seedless project halt. An empty value is schema-valid.
- **Asset layout.** Where screenshots and other assets from `capture.output_dir` are referenced from inside the chapter file. If the target requires assets to live in a target-specific location (e.g. uploaded to a Confluence attachment endpoint), document the move/copy step.
- **Link format.** Whether links between chapters use `publish.wikilinks: true` (Obsidian-style `[[Target]]`) or plain Markdown `[text](path)`. If the target supports both, say which to prefer and why. If the target ignores `publish.wikilinks`, say so explicitly.
- **Section labels.** How `publish.section_labels.prerequisites` and `publish.section_labels.related` are substituted into the chapter — usually verbatim under H2 headings, but the target may impose a different heading level or a structured field.
- **Group handling: support or halt.** 1.5.0 adds an optional two-level grouped nav — a manifest entry may carry `group` + `group_title` (see `manifest-discipline.md`); the axis is active the moment ANY entry in the manifest carries `group` (`anyGroup`). If your target can express two levels of nav, mirror the shipped adapters' group-aware chapter path and asset dir (see "Chapter path" and "Assets" in `static-md.md`, or the equivalent in `obsidian-vault.md`) and their index-wiring machinery — container find/create/append, the step-0 presence scan, and the wrong-container / duplicate-line / near-miss / manual-wiring halts (call that third one the NEAR-MISS halt, not the "ambiguous-container" halt — this plugin already uses container-ambiguous for the MULTIPLE-candidate outcome, see `chapter-paths.mjs`). **The create branch is CONDITIONAL, not automatic (#476).** A zero label match is two facts wearing one name — this group has no container yet, or one exists and the equality compare failed for a reason the match cannot see — so before creating a container because the label match came back zero, your adapter must ask whether an existing heading merely RENDERS as `group_title` (NFC, case folding, a whole-content emphasis/link/wikilink/inline-code/inline-HTML wrapper, a resolved character reference, a trailing `{#anchor}`, a leading OR trailing run of ORNAMENT — an emoji, an icon, a bullet glyph, a punctuation run, meaning a run carrying no letters and no digits — those are the common cases and NOT a closed list, so treat any unnamed rendered equivalence as a near miss too, since the cost of doing so is a halt and the cost of missing one is a forked index). Do NOT fold a run that carries letters or digits: `Reports (2024)` and `Reports (2025)` are two sections an operator maintains side by side, and folding the parenthetical halts a correct handbook with nothing that clears it, since the token that distinguishes them is the token folded away — stripping is not rendering. Run that compare a SECOND time with the unsafe invisible characters removed from both sides — the set `isPlainLabel` already refuses (`INVISIBLE_LABEL_CODE_POINTS`), which spares U+200C/U+200D by construction because those are required inside ordinary Persian and Hindi words — and when it matches, name the offending code point and its offset, since nothing else makes it visible; folding the whole invisible class instead would lock out correctly-spelled titles, and folding none of it leaves a silent permanent fork (#553). Then, if one does, halt naming `group_title` and EVERY candidate heading rather than just the first. Have that halt prescribe NO repair: whether these are one section spelled several ways or several sections that render alike is a question about what the sections MEAN, which a spelling comparison cannot reach, and a halt that guessed would tell the operator to merge a section they curated into an unrelated one in exactly the over-rejected case this branch deliberately accepts. Report and hand the file back, the way the multiple-container halt does; it names no form, so it promises no convergence. That comparison detects a near miss and never selects a container to write into, so it cannot mis-target; an unconditional create instead forks a hand-curated index in two, reports success, and never self-corrects, because the next run matches the heading it wrote itself. **Step 0 alone does NOT make re-runs converge — 1.11.0 measured both ways it fails, and a new adapter that mirrors only step 0 reproduces them.** Step 0 recognizes a row by parsing a link target out of it, so a manifest `title` that breaks its own row's target parse is reported absent forever: with a `-` child that appends a duplicate row on every publish without limit, and with a `*`/`+` child it writes one row whose raw grouped target makes every later scan refuse the whole file. Your adapter needs the writer-side pair that bounds these — a literal, content-verbatim membership check that does not reuse step 0's parse (returning `present`), and a re-read of the exact bytes about to be persisted through the same reader that will parse them next run (returning `unwritable`, writing nothing). Both guards are only half the contract: they change what the WRITER returns, and your adapter must branch on it. The writer returns five outcomes and the caller's obligation for each is fixed: persist the new lines ONLY on `{kind: 'inserted'}`; halt on `{kind: 'present'}` (the row is already there and this run could not recognize it, so continuing reports a completion that did not happen); halt on `{kind: 'unwritable', field}` naming the offending field and its recovery class, having written NOTHING; halt on `{kind: 'multiple'}` rather than guessing a container; and route `{kind: 'not-a-list'}` to the manual-wiring halt. Logging-and-continuing on `unwritable` is the specific mistake to avoid — the writer protects the index by refusing, and a caller that treats that refusal as non-fatal reports a published chapter with no index row at all. Note also what the literal membership check is keyed to: the COMPLETE current link string. It bounds re-runs of an UNCHANGED manifest entry and nothing beyond that — edit a target-breaking title and the next run is handed a link string the check has never seen, so it correctly finds no match and inserts. Bounding what an EDITED title leaves behind is a separate obligation with its own bullet below — see "Leftover index rows". And when a chapter's line is already present in a NON-HEADINGS index, the adapter must call `verifyNonHeadingPlacement` and branch on all four outcomes — `ok` proceeds, `misplaced` halts naming the container it actually found, `inconsistent` is a fail-closed contradiction check, and `unverifiable` means the check declined to conclude and the run continues UNVERIFIED, exactly as it did before 1.11.0. **That last rule is ESTABLISHMENT-time only — do not carry it into W6.** W6 calls the SAME verifier for a `group_title` migration — the difference is what each outcome means there. The migration's `title-container` fact holds on `ok`; `misplaced` and `inconsistent` re-halt exactly as at establishment; but `unverifiable` requires this checklist's own EXPLICIT USER CONFIRMATION before the move may be called complete, where establishment would simply continue unverified. Do not confuse this with the old-target-absence facts: those are emitted only for a group PATH change or a removal, never for a pure `group_title` change (measured — a title-only delta emits `title-container` alone), and the verifier is not their instrument, since it proves where a PRESENT row sits rather than that an absent one is gone. `references/revalidation.md` draws the split itself, under "Retained entry, `group_title` changed": the migration checklist keeps explicit confirmation for `unverifiable`, and says of the adapters' establishment-time placement check, in those words, that it is the flow "which requests none on its own `unverifiable` outcome". A new adapter must therefore state its W6 behaviour separately from its establishment behaviour; reusing the continue-unverified rule for a migration silently reports a completed group-title move that was never proved. Skipping that call preserves 1.10.0's presence-only behaviour, which silently accepts a chapter sitting under the wrong container. See `wireNestedListChapter` and `verifyNonHeadingPlacement` in `assets/lib/chapter-paths.mjs`, their declarations in `chapter-paths.d.mts`, and the "Grouped index wiring" and "Nested-list automation limits" sections of either shipped adapter — gating that index-wiring machinery on `anyGroup(entries)` so a group-free manifest skips it. **Not every branch should be gated this way.** Three exceptions are in `assets/lib/chapter-paths.mjs` — `staticEmbedPath` (the asset-embed path formula, always the full-target `relative()` join, never a legacy concatenation), `validateGroups` (the duplicate-slug halt — globally unique across all groups by default, or unique within each group when the consuming profile sets `publish.per_group_slug_uniqueness: true`, which re-admits cross-group and flat-vs-grouped basename collisions for bare-`[[slug]]` / Quartz-shortest consumers — see `manifest-discipline.md`), and `currentIndexExpectedTarget`'s wikilinks-mode index-target formula (vault-root-relative since 1.8.0, regardless of grouping — see `obsidian-vault.md`'s "Wikilinks vs Markdown links") — model your target's embed formula, duplicate-slug check, and (if your target has an equivalent wikilink-style bare-name resolution) index-target formula on those, ungated. Your own adapter may ALSO have group-free behavior changes beyond those three module-level exceptions — for example, in `publish.wikilinks: false` mode `obsidian-vault.md` applies the full-target glossary formula and runs the Markdown-link integrity gate for group-free manifests too — so do not assume `anyGroup` gating covers every branch; state explicitly, per section, which behaviors apply to a group-free manifest. If your target cannot express two levels of nav, it MUST halt the moment it sees any entry carrying `group` — never silently flatten a grouped manifest into a flat layout, and never drop `group_title`. State explicitly in your adapter file which case applies. Nested groups (`a/b`) are out of scope for every adapter in 1.5.0.
- **Halt conditions.** Any precondition the adapter must check before writing (e.g. the index file exists, the chapters_dir is writable, the target's required tooling is reachable). List the exact halt messages.
- **Address derivation.** One formula per link class, each naming the coordinate system it starts from and the one it produces. Link SYNTAX (the bullet above) and coordinate SYSTEM are independent choices, and getting the first right leaves the second entirely undecided — see "Address derivation" below for the required per-class list and the shipped pair's worked divergence.
- **The completion gate.** An ordered list of target-specific checks that must pass before the run may report the chapter published, halting on the first failure — see "The completion gate" below.
- **Leftover index rows.** Step 0's presence scan and the writer's membership check both key on the link THIS run would write, so neither ever sees a row an EARLIER title left behind. Your adapter needs a THIRD scan alongside them, doing the job neither does: find the rows that ADDRESS this chapter without RESOLVING to it, and halt naming every one of them, with its line number and its raw text, before anything is written (`findStaleChapterRows` in `assets/lib/chapter-paths.mjs`, #349). Decide "is this row the one THIS run would write" by ROW SHAPE, in two directions, because the two populations have opposite safe failure modes. On the shape your own writer emits, compare EXACTLY against the row's own content: a title ending in the next title's opening bracket makes the row it emits CONTAIN the next run's whole link, so a containment test there skips the very row it exists to report — measured, three rows accumulated and none was named. On any OTHER shape, use containment and let the scan go SILENT: your flat branch appends whatever the file's convention is, so the shapes are open-ended, and an exact comparison against one you did not anticipate names the row the adapter itself just wrote — the operator deletes it, the next publish re-appends it, and the halt never clears. An over-report is only cheap while it stays clearable. REPORT those rows; do not delete them. The index format carries no row-to-chapter ownership record, so a row this tool could have written and one an operator hand-authored around an unparseable link are indistinguishable, and only the operator can tell them apart — the same reason the near-miss halt prescribes no repair. Run it for every entry and every index form, not only the grouped nested-list one — a leftover addresses the chapter the same way whichever branch wired it. Be exact about what that buys, though, because the obvious reading is wrong: the scan keys on the link THIS run would write, so it reports a row an earlier TITLE left behind and is blind to an identical row your own append branch wrote a moment ago. Bounding THAT is the append branch's own obligation and has its own bullet below. That the two scans never return the same row, and that a longer target carrying yours as a prefix or a suffix is not reported, are properties enforced by the `#349:` tests in `tests/chapter-paths.test.mjs` — read them rather than trusting this sentence.
- **Read your registration back before you write it.** The scan above reports what an earlier title left behind; it is blind by construction to an identical row your own append branch just wrote, and bounding THAT is your APPEND branch's own obligation. The shipped adapters discharge it by REFUSING rather than by recognising (#574): before you register the chapter, apply your own step 0's recognition semantics to the registration you are ABOUT to make, WITHOUT persisting it, and if the answer is "my next run would not find this", register nothing and halt naming the chapter's title as the thing to change. For a file target that is literal — compose the row and read it back through the very call your step 0 makes over the file, `locateChapterLine([row], expectedTarget, <the same options>)`. For a target whose registration is an API call with no side-effect-free validation or dry-run, there is no honest read-back available: halt for manual wiring rather than write and hope. Refusing is the obligation an adapter in another format inherits; the file-shaped spelling of it is not, and the property that must hold is representation-neutral — "the reader this target's next run will use can find the registration this run made", which only that reader can answer. A membership check that recognises the unreadable row instead — the flat analogue of the writer's `present` outcome — bounds the count at one but leaves a row every later run must special-case, and it is deliberately not what ships.
- **Revalidation and W6 integration.** What a group change means for your target's own object model, which changes it may perform, which it must halt on, and what evidence constitutes a verified terminal state — see "Revalidation and W6 integration" below. Every bullet above this one is establishment-time; this is the one that fires afterwards, when the manifest changes.

Keep the adapter file to roughly the same shape and length as `obsidian-vault.md`. Reference profile keys exactly as written in the profile schema (e.g. `publish.chapters_dir`, not "the chapters directory"). Do not duplicate generic discipline (anti-fabrication, completeness, glossary policy) — that lives in the sibling `references/` files and applies regardless of target.

## Address derivation

`publish.wikilinks` picks a link SYNTAX. It says nothing about the COORDINATE SYSTEM an address is measured in, and the two are independent: you can pick the right syntax and still derive the wrong destination, because nothing about `[text](path)` tells you whether `path` is measured from the linking file, from a tree root, or from nothing at all. State one formula per link class. For each, name (a) the ORIGIN the address is measured from, (b) the normalization applied to the operands before the arithmetic, (c) the address produced, and (d) whether it is depth-sensitive — i.e. whether two chapters at different group depths get different addresses for the same destination. The classes are: index -> chapter, chapter -> chapter, chapter -> glossary (including the anchor derivation), chapter -> asset, and chapter -> handbook index.

That the shipped pair AGREE on syntax within a mode and still DISAGREE on origin is the whole reason this section exists, so read the divergence before assuming a class is settled. Index -> chapter: `static-md.md` measures from the index file's own directory (`relative(dirname(index_file), chapter_file)`, `.md` kept), while `obsidian-vault.md` under `publish.wikilinks: true` measures from the vault root and drops one terminal `.md` (`currentIndexExpectedTarget`'s wikilinks branch in `assets/lib/chapter-paths.mjs`). Chapter -> asset: both use the full-target `relative()` join (`staticEmbedPath` / `embedPath`), ungated by `anyGroup` — that one class is settled for every file target and you should mirror it rather than re-derive it. Chapter -> glossary: each adapter has its own glossary canon and neither reuses its chapter-link formula for it, so a target that folds the two classes into one address form is wrong in at least one of them. Chapter -> handbook index: `static-md.md` requires the link and derives it depth-sensitively; `obsidian-vault.md` has no equivalent mandatory one.

Three rules bind every formula you write. **Never bake a raw `publish.*` value into an emitted address** — derive it, so a profile that spells the same location differently still produces one address. **Apply the normalization to BOTH operands**, and say which normalization: an address you WRITE and an address you SCAN for must be byte-identical after it, or your own step-0 scan will not recognize your own rows and every run appends a duplicate. **Fail loud rather than falling back** when an operand is missing or out of range — `currentIndexExpectedTarget` throws on a null, absolute, or leading-`..` vault-relative prefix precisely because the silent bare-slug fallback it replaced resolved ambiguously across a whole vault (#294); copy the shape, not just the intent. And if your target's address form ever changes, state the union scan and its four-way verdict — `classifyChapterWiring` returns `absent` / `canonical` / `legacy` / `duplicate` — so an existing row in the old form is retargeted in place instead of becoming invisible, and an ambiguous pair halts instead of forking the index.

**Where your formula stops being consulted.** `currentIndexExpectedTarget` admits exactly two derivations, selected by `publish.wikilinks`, and throws otherwise. A third target cannot register its own, so the index-membership facts the module emits during revalidation (`current-index-membership`, `flat-membership`, `old-index-target-gone`) are computed by one of those two formulas whatever your adapter says in prose. Write your formula down; do not claim those emitted facts reflect it.

## The completion gate

Every adapter must end with an ORDERED list of checks that runs after the chapter is written AND after the index/parent wiring, halts on the first failure, and closes with the verdict both shipped adapters state verbatim: a chapter that fails any of these is unpublished, not "almost done" — fix and re-verify. Without it, nothing stops a run reporting success on a chapter whose assets, links, metadata, or index row never landed. The SHAPE is fixed; the item list is not. Both shipped gates carry five items in the same order, and the items themselves differ — that difference is the contract, not an inconsistency to smooth over.

Cover, at minimum: every asset reference resolves to something that exists in the derived location AND stays inside your target's containment boundary; every internal link resolves, with anchors checked against the thing they name and a stated exemption list for addresses this gate does not own (external schemes, absolute paths); a navigability floor; the metadata written back reads back unchanged; and the index or parent lists this chapter, proved by RE-READING it. That last one is the item most often written as a no-op: **the wiring step returning success is not evidence that the chapter is listed.** Re-read the index in its own coordinate system and confirm the row is there, or a chapter whose wiring silently failed ships as published with no way in.

Two items are target-specific in a way that makes copying either shipped adapter actively wrong. **Containment**: `static-md.md` requires `capture.output_dir` to resolve under `publish.chapters_dir`, because a static renderer serves only what is inside the docs tree; `obsidian-vault.md` requires the resolved target to stay inside `<vault-root>` and says in as many words that it is **not** required to sit under `publish.chapters_dir`. Two shipped adapters, opposite requirements, both correct for their own target — so state yours and justify it from what your renderer can actually serve. **The navigability floor**: `static-md.md` takes one resolving link back to `publish.index_file` as the minimum bar and explicitly declines to require a second, because a static site has no graph view; `obsidian-vault.md` requires at least two outbound links in the Related block, because Obsidian does. State your floor and derive it from your target's own affordances, never from the other adapter's number.

Say what the gate does NOT cover, in the adapter, next to the gate. It is chapter-scoped: it fires when that chapter is published or touched by a revalidation, a no-op revalidation never runs it, and it does not sweep untouched chapters — a stale link in a chapter nobody republished stays broken. It is a RESOLUTION check, not a spelling check: a retained chapter's older, still-resolving address stays valid and is never rewritten, and no chapter is rewritten solely because a canon changed, a version was upgraded, or `anyGroup` flipped. And index-wide alias or broken-row checking is out of scope — a divergent hand-authored row is retained beside the canonical one (`locateChapterLine`'s path-mode byte-identity rule, #311), so the gate passing does not mean the index has exactly one row per chapter.

## Revalidation and W6 integration

Everything above is establishment-time. When the manifest itself changes, a second contract applies, and an adapter that documents only establishment leaves the migration path undefined for its target — the failure is silent, because establishment machinery will happily wire the current manifest as if it were new. Your adapter must state all of the following, in its own object model.

**Establishment never renames, moves, or deletes.** Say it explicitly, in the index-wiring section, even if it seems obvious for your target — it is least obvious exactly where it matters most, because an API target can re-parent or retitle in one call with none of the friction a filesystem imposes.

**What a group change MEANS for your target, per delta kind.** `groupChanges` classifies each retained or old-only entry into a closed set — `removal`, `group-change`, `title-change`, `group-and-title-change`, or none at all — and a new-only entry never produces a kind, however grouped the manifest becomes. Presence is tested as `entry.group !== undefined`, never truthiness. Re-express each kind as an operation in your own model and say which of them your target can perform and which it must halt on. Both shipped adapters perform NONE of them: every kind reaches the manual-migration boundary and halts.

**What evidence constitutes a verified terminal state**, fact by fact, and — the part that is easy to skip — which facts are mechanically provable and which resolve only by EXPLICIT USER CONFIRMATION. The shipped model draws that line deliberately: a capture spec is arbitrary user code, so a hit is decisive negative evidence while an absence proves nothing and falls through to confirmation. Your target will have its own facts of both kinds; a checklist that claims to prove what it cannot is worse than one that asks.

**The halt.** Three parts: a fixed opening line, one record line per changed entry carrying every old and new coordinate the operator needs, and a pointer to the recipe. It has to be reconstructible from its own text, because a later run may have no manifest history at all. Do not print a placeholder or an empty coordinate; if your target has no analogue for a field, omit the fragment rather than render it hollow.

**The rest of the lifecycle, each stated for your target:** the post-migration handbook-wide link scan and its fixed retry order (re-verify every terminal fact, then repeat the scan, then re-run the touched-chapter gates — a fact can regress while the operator is fixing the reported links); the stale-artifact advisory, which runs on EVERY run, is never a halt, never deletes, and reports artifacts not derivable from the CURRENT manifest, because a manifest edited outside the review flow leaves orphans with no delta to trigger the boundary; and that an `anyGroup` flip is always informational and never suppresses a migration kind the same delta carries — kinds always win, and losing the manifest's last grouped entry is itself a removal that still halts for cleanup.

**Audit the shared recipe rather than inheriting it.** `references/revalidation.md` carries an eight-step manual recipe written in the shipped adapters' terms — move the chapter file, move the asset directory, retarget the index line, rewrite embeds and links, fix inbound links, update the capture spec. Read every step against your target and say, in your adapter, which have an analogue and which do not. Silence is not "not applicable": an operator reading a recipe step that names a file path for a target with no files has no way to tell whether it was omitted deliberately or forgotten.

**W6 differs from establishment on one outcome, and only one.** The `verifyNonHeadingPlacement` split is stated in the "Group handling" bullet above: at establishment `unverifiable` continues unverified with no confirmation requested, while for a `group_title` migration it requires explicit user confirmation before the move may be called complete. State your W6 behaviour separately from your establishment behaviour rather than letting a reader assume they are the same.

### What this contract cannot yet require

The obligations above are prose obligations. Today there is no per-adapter extension point for any of the machinery that would verify them, and a contract that implied otherwise would be worse than one that says so.

`manualMigrationChecklist` emits a FIXED set of twelve fact kinds — measured, not estimated — computed from the two manifest entries plus a profile shape typed to `capture.output_dir` and `publish.chapters_dir` / `index_file` / `wikilinks`. Eleven of them carry a local file path, an index target in one of the two hard-coded coordinate systems, or a capture-spec directory spelling; the twelfth, `title-container`, carries the manifest's own `group_title` strings and no path at all. What none of them can express is a page id, a parent, or an attachment. There is no target parameter and no registry, so a target whose terminal state is "this page sits under that parent, with these attachments" can describe those facts in prose and cannot make the module emit them. `renderManualMigrationHalt` composes its record lines from that same fact set with no formatter hook, and its opening line and recipe pointer are string literals; a non-file target can only print coordinates that do not exist for it or bypass the shipped renderer entirely. `migrationRecordPath` hardcodes `<publish.chapters_dir>/.provenance/chapters/<group>/<slug>.json`, so a target whose provenance does not live under a local publish directory has nowhere to declare where it does (#380). `verifyNonHeadingPlacement` consumes index LINES and returns its four outcomes from text scanning; there is no hook for a page-tree verdict producer, so its outcome names and semantics can only be mirrored in prose, with nothing pinning the mirror to the module.

The consequence, stated plainly so nobody has to rediscover it: a third adapter's revalidation contract is prose-only. It can be written, reviewed and followed by a human operator, and none of it can be machine-verified by this plugin until the fact set and the halt renderer gain per-target extension points. That is a separate change, and it is not a prerequisite for writing the adapter — it is a prerequisite for trusting the adapter's migration path the way the shipped two are trusted.

## Naming

The filename is the contract. `publish.target: obsidian_vault` reads `obsidian-vault.md` (underscores in the profile value become hyphens in the filename, lowercase throughout). Keep names short, descriptive, and free of vendor versioning — `confluence.md`, not `confluence-cloud-2026.md`. If a target genuinely needs two variants (e.g. Confluence Cloud vs. Server with different APIs), use `confluence-cloud.md` and `confluence-server.md` and let the consumer pick via `publish.target`.
