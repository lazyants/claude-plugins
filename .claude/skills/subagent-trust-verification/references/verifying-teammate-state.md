# Verifying teammate state: stale reads, report lag, duplicate agents

Three ways a shared-cwd team's on-disk/report state misleads if read carelessly: your OWN cached read goes stale, THEIR report lags THEIR disk, and a liveness misjudgment spawns a second agent onto one work-unit. All three share one discipline — verify against the live filesystem/transcript, never against a narrative or a memorized snapshot.

## Don't correct a teammate off a stale read

Verified 2026-07-08 (literary-translator assembler build, orphan_verse reviewer round). Teammates in a shared cwd edit the same files LIVE, so the disk moves between your reads. Read `assemble.py`, saw an "exemption" approach at a cached line, sent teammate B a fix message; re-read (still the stale snapshot — B was mid-edit) and fired a SECOND "SUPERSEDES — revert to the exemption" message. But B had ALREADY landed the *better* scan-based approach (the one codex round-2 then confirmed was gap-free). The superseding message was simply WRONG about what was on disk. B and D both had to stop and flag "your description doesn't match the file" — they were reading fresh each time; the lead was reacting to a cached mental model. It also told D to SKIP a boundary test that was actually correct for the real (scan) approach. Net: avoidable churn + teammates spending a round reconciling the lead's confusion instead of doing work.

**The rule: before sending a teammate a CORRECTION or a superseding instruction, RE-READ the current file.** A correction is higher-stakes than a first instruction — if it's wrong it creates conflicting messages the teammate must untangle, and can make them re-implement over already-correct work. The first instruction off a slightly-stale read is cheap to fix; a *superseding* one off a stale read is expensive.

**Trust fresh reads over your mental model.** The teammates' on-disk reports AND codex's read were all consistent with each other and with the disk; only the cached snapshot disagreed. When N independent fresh reads say X and your memory says Y, your memory is the stale one — re-read, don't argue from the snapshot.

**Convergence pattern that avoids the whole class:** don't react to mid-edit snapshots at all. A stream of diagnostics whose LINE NUMBERS keep shifting = someone is mid-edit; HOLD. Let every teammate report done + idle, THEN read the disk ONCE on the settled tree and run codex on it. Reserve mid-flight messages for genuinely new information, not corrections of a moving target.

**Standalone-verifier trick when you must verify an invariant that IMPORTS a mid-edit file.** 2026-07-09: the lead needed to confirm a SHA-1 region hash of `extract.py.template` after every teammate edit, but the canonical `selfcheck_region_hash` lives in `validate_extraction.py`, which ANOTHER teammate was concurrently editing (importing it mid-edit risks a syntax error / half-written state). Fix: INLINE the ~5-line algorithm into a standalone scratchpad script that imports nothing from the moving files (just reads the target's bytes and computes). Decouples verification from unrelated in-flight edits so the invariant can be checked any time without waiting for that teammate — trust-but-verify without a race. General rule: a verifier should depend only on what it's verifying, not on a sibling file that happens to hold the helper.

**Multi-generation / multi-session teams: a single-owner file changing under you is probably YOUR OWN teammate, not a hostile clobber — verify authorship BEFORE escalating to the user.** 2026-07-18 (plugins-migration build): named agents re-spawned came back suffixed `-2` (`orchestrator-2`, `unit-tester-2`) because the PRIOR (pre-compaction) generation still held the bare names and was alive. When `pm.py`'s mtime kept advancing with fix-shaped edits that hadn't been dispatched — plus a transient 11-test-fail + an undefined-symbol Pyright flash — this nearly triggered a "a parallel session is clobbering our data-safety file" alarm at the user. It was `orchestrator-2` (the lead's own re-spawn) resuming after a context reset, finding the PENDING-FIXES.md task list on disk, and applying exactly the fixes already staged (autonomous self-dispatch); the fails were mid-refactor snapshots. Diagnose before alarming:

1. `stat` the file twice across a delay — advancing mtime = a live editor.
2. Read the changed regions — edits matching your own staged list are your team, not hostile.
3. Attribute via the shared task-doc checkboxes + a direct `SendMessage` ("did you author the 23:05 edits?").
4. The `-2` name-collision is itself the tell a prior generation is alive.

Crying "hostile collision" wolf erodes trust as much as a real one; confirm it's your own team first, and only if it's genuinely a foreign session unreachable via `SendMessage` do you surface it to the user for arbitration.

**Corollary (reviewer freshness):** a reviewer dispatched against bytes that have since moved returns findings that are partly STALE (already fixed). Before dispatching fixes, verify each finding live-vs-stale against CURRENT source (grep the exact symbols); don't chase already-fixed findings or skip genuinely-live ones.

This is the mirror image of report lag below: there the TEAMMATE's report lags their own disk edits; here it's the LEAD's read that's stale.

## Report lag: verify the round-specific NEW symbol, not the narrative

When driving multi-round fix work through named teammates (`builder`/`tester`), completion reports repeatedly lagged a **full round** behind their actual filesystem edits: each message confidently re-described the PREVIOUS round's deliverable while the CURRENT round's edit had already landed on disk (or was still landing). Twice this nearly led to re-dispatching already-done work.

**Two false-comfort traps, both defeated by the same check:**

- The report NARRATIVE may describe round N-1 even when round N was requested — don't trust it.
- Re-running the test suite stays GREEN across rounds (each round adds tests that pass), so "55 passed" does NOT prove round N's specific fix landed.

**How to apply:** after dispatching a round-N fix, verify the round-N deliverable by `grep`-ing the file for its round-SPECIFIC new symbol (the new constant / function / `except` clause / removed line) AND running the one targeted test — BEFORE either re-dispatching (avoids duplicate work) or banking it. The on-disk grep is what disambiguates; the report text and the suite pass-count do not. Edits reliably land FASTER than reports arrive, so a disk check a beat after dispatch usually already shows the change.

**Sharper form — re-run the FIX'S BEHAVIOR yourself, not the teammate's pasted repro.** A teammate's "before/after" paste can exercise the WRONG code path and still look green. Verified: a deep-nesting test at too-shallow depth (`"["*100000...` on CPython 3.14) PARSES fine and is caught by an unrelated structural check, never reaching the `RecursionError` branch it claims to test — the report + suite both stay green while the intended path is untested. So independently reproduce the fix's OUTPUT (exit code + the round-specific message) against your own input, especially when a test hinges on a threshold/size/depth parameter you (or the teammate) guessed.

**Silence: no report arrives at all** (2026-07-11, literary-translator 1.3.3 review loop). Several teammates went straight to `idle_notification` with zero completion-report text after finishing a dispatched fix — no narrative to distrust, just silence. Same fix applies: don't wait for a report that may never come, and don't re-ask the teammate — go straight to `git diff --stat`/`grep` for the round-specific symbol and run the tests yourself. This happened 3+ times in one session with genuinely-complete work every time, so silence alone is not a red flag — treat it identically to a report you don't fully trust.

**Report-only deliverables: idle-with-`[to main]` means already delivered** (2026-07-12, plugin-gap investigation). For REPORT-ONLY deliverables (investigation/audit/research — nothing lands on disk), the deliverable IS the message, and the idle notification reliably arrives WITHOUT it. 8/8 background teammates that session (7 investigators + 1 PR builder) went `idle_notification` with no deliverable text; ONE `SendMessage` nudge each ("reply via SendMessage to \"main\" with your FULL deliverable") retrieved the complete report every time, usually within a minute. A LATER idle notification carrying a `"summary":"[to main] …"` field means the deliverable WAS already sent — that one is just a confirmation, don't re-nudge. So: disk work → verify on disk (above); report-only work → first bare idle = nudge once, idle-with-`[to main]`-summary = already delivered. Also confirmed: outward actions (`gh issue create` / PR) by the teammate ARE real even when the report is stuck — verify via `gh pr list`/`git worktree list`, which can beat the report by minutes.

**Total silence, not even an idle notification: harvest from the subagent transcript, don't nudge and don't re-run** (2026-07-19, 29-issue audit fan-out). Five parallel audit agents completed at 12:55–12:57; no completion notification, no idle ping, nothing. Silence is indistinguishable from "still working" — telling the user "a few more minutes" continued for 23 minutes and was only checked because the user pushed twice ("долго ещё?", "точно не завалились?"). Two-step recovery:

- **Liveness first, but know what it does NOT tell you.** Two `stat`/`ls` snapshots ~20s apart prove the transcripts are not growing. That distinguishes "not progressing" from "working" — it does NOT distinguish DIED from FINISHED; a first read of a 23-minute-stale mtime as "stopped" was the wrong read. Read the LAST entry of the transcript: `stop_reason: end_turn` on an `assistant` record means it finished cleanly and the deliverable text is right there.
- **Harvest from the subagent transcript.** Final report = the last `type:"assistant"` message's text in `~/.claude*/projects/<cwd-slug>/<SESSION-id>/subagents/agent-a<name>-<hash>.jsonl`. Extract with a streaming parser (never read raw JSONL into context — files were 215–285 KB each). Strictly better than a `SendMessage` nudge: no round-trip, no risk of RESUMING a completed agent into redundant work. Path gotchas: the `subagents/` dir hangs off the **session** id, not the id used in scratchpad task paths; and it can live under a different profile dir (`.claude`) than the one currently running (`.claude-bm`) — so `find ~/.claude*/projects -name 'agent-a*<name>*' -mmin -60` instead of assuming either.

**A content-grep completion watcher fires on PARTIAL mid-edit state** (2026-07-15/16, SSK index-fix). When arming a background watcher (an `until grep -q <marker>` loop) to detect a teammate's edit landing, grepping for a new symbol/constant/string fires on its FIRST appearance — often BEFORE the surrounding logic is wired: a constant defined but not yet referenced ("unaccessed"); a field present but not yet wired into its consumer list; a test-count of +1 when 3 tests were expected. Fired 3-4× in one session, each forcing a re-armed stricter watcher and a near-misread ("teammate mis-reported" when it was mid-edit). Fix: prefer a BEHAVIORAL watcher — run the actual check (does the targeted test PASS? does the function produce the expected OUTPUT on a probe input?) rather than grep-for-marker, which is robust to partial edits.

**A timely, honest test-failure report can be a false negative from CONCURRENT shared-worktree activity** (2026-07-17, literary-translator skeptic-pass build). Four teammates each ran the FULL suite at once in the shared worktree; one reported a `FileNotFoundError` flake in ANOTHER owner's test (a per-run tmp file) that PASSED standalone AND on re-run. Root cause was environmental — a test reading a sibling's file mid-rewrite / a pytest tmp-dir race under concurrent suites — NOT a bug, and not a mis-report either. Fix: before dispatching any fix for a teammate-reported failure observed during concurrent multi-teammate suite runs, the LEAD re-runs it SERIALLY (the file alone, then the full suite) — a green serial run dispositions it as a concurrency artifact. Chasing it as a real bug, OR blaming the teammate, is the miss.

**Inverse trap: disk can lag an ALIVE teammate's in-progress work — don't re-dispatch off a clean `git status`** (2026-07-11, enduser-handbook #110 build). The `core` teammate was mid-build; running `git status` EARLY (before its first save landed — the edits arrived ~minutes later) showed the contract file unmodified with no completion report, which was read as "core is dead" — and in the SAME turn, both a status-check AND a fresh `impl` teammate to rebuild the same file went out. Both then edited the same file (`profile-version.mjs`) in the shared cwd. It resolved benignly (both targeted the same frozen contract; last-writer-wins left a coherent file), but it was luck, not design. The miss was procedural: **not WAITING for core's reply before re-dispatching.** Fix: when a teammate's work isn't on disk yet, MESSAGE it and WAIT for the answer (alive-but-mid-edit vs actually-dead) before spawning a replacement for the same file; a clean `git status` a beat after dispatch means "hasn't saved yet" at least as often as "died".

**A report that UNDER-claims is still a report — check the ARTIFACT, not the self-description** (2026-07-20, literary-translator 1.11.0). A teammate's chat summary said its file left a limitation uncovered "at all sites"; the FILE actually named the one uncovered site correctly and listed the three covered ones by test name. Firing a correction at the file based on the summary nearly rewrote prose that was already right; the teammate pushed back with line numbers instead of complying. Two lessons: (1) a working rule of "don't trust a report that claims SUCCESS" is incomplete — pessimistic/humble self-descriptions are not pre-verified either; the correct rule is *act on the artifact, never on the report*, in either direction. (2) An "uncovered everywhere" claim needs the same experiment as a "covered everywhere" claim.

## Duplicate agents on one work-unit in a shared cwd

Two agents ending up on the same work-unit in one shared cwd arises two ways; both produce the same hazard — two agents owning the same files, which is exactly how an unaccounted-for / half-clobbering edit lands. Contained both times only because the duplicates happened to verify rather than clobber — do not rely on that luck.

**Trigger 1 — reusing a still-ALIVE name (silent twin).** Verified 2026-07-20 (literary-translator 1.11.0). Dispatching a new round under the SAME names as the previous round (`A2c`, `A3b`) without realising those agents were still alive and idle: the harness did not error or reuse them — it created **`A2c-2`** / **`A3b-2`**, and both generations then existed at once. The OLD `A2c` truthfully reported it had touched nothing (true — the edits were the new twin's), and the escalation read as *an unowned agent editing production files*. Nothing was wrong, but that is indistinguishable at first glance from a real rogue edit. Message names resolve to the LATEST holder, so addressing `A2c` after `A2c-2` exists may not reach whom is meant.

**Trigger 2 — re-dispatching after wrongly concluding a mid-flight agent DIED.** Verified 2026-07-24 (enduser-handbook 1.10.0, #223). After a `/compact`, checking the worktree and seeing `git status` CLEAN led to concluding the compaction had killed the Phase-1 agents and their work was lost — so the same work was re-dispatched under FRESH names (`EH-CORE-b`, `EH-DOC-b`). The originals were actually **alive and mid-flight**; the clean-disk check was a snapshot taken before they had flushed. Minutes later the originals reported complete → two agents (different names) had been racing on the same files. The `-b` duplicates wisely verified-not-rewrote, so nothing was clobbered, but a concurrent write race on the same module could have produced a half-merged file.

**Trigger 3 — the liveness PROBE is itself a resurrection event, so check-then-re-dispatch in one turn is a race by construction.** Verified 2026-07-26 (enduser-handbook 1.11.0). A named teammate went **two hours** with zero edits on disk and no answer to a status ping — far past the short flush windows above, and about as close to proof of death as this evidence ever gets. The work was re-dispatched to a fresh agent. The ping then woke the original, which resumed editing the very files the replacement now owned. Both adapter documents were being written while the new agent was investigating; it caught the collision only by noticing an mtime **30 seconds old** on a file its brief called clean, and stopped before writing. So the length of the stall is not the variable — *a stalled agent is dormant, not dead, and your probe is what ends the dormancy.* Send the probe and WAIT for the answer as a separate step; never in the same turn as the replacement dispatch.

**A clean working tree mid-run is a snapshot, not proof of loss.** After a compaction/interruption, do NOT infer a dispatched background agent is dead from a clean (or empty) tree — a live agent that hasn't written yet looks identical to a dead one.

**How to apply:**

- Use a FRESH name per round (`A2c` → `A2d`), and **stand down** agents you are done with rather than leaving them idle-but-live (still named, still addressable).
- **Before RE-dispatching work thought to be lost, verify the original is actually dead/done — not that the disk merely looks empty.** Wait for its report, or check liveness (a live agent will still message/idle-notify); a clean tree alone settles nothing. Re-dispatch only after confirming.
- **If a duplicate is discovered running: FREEZE first** (message both to stop, do not write), then verify on-disk COHERENCE (syntax + full suite, not just presence) to tell a clean single-author result from a half-clobbered one, then commit the verified-good state as a restore point, then stand the duplicates down. An uncommitted good state is MORE vulnerable to a late clobber than a committed one.
- **Committing the blend is only right when the work is COMPLETE and verifiable. When the duplicate's edits are partial and no check was ever run on them, preserve them as a patch file and `git checkout --` back to the last commit instead** — then hand the patch to the single surviving owner as a *reference draft*, explicitly not a base. A half-applied edit whose provenance you are guessing at cannot be verified, only re-derived, and starting the survivor from a known commit is what makes its later report checkable. Sample the mtimes until they hold steady BEFORE resetting: in the 2026-07-26 case the file was written once more *after* the freeze message and *after* the patch snapshot, so resetting on the first quiet reading would have preserved a state that no longer existed and discarded the real one.
- A truthful "I haven't touched that" does not mean nobody has; a clean tree does not mean the agent is dead. Both readings of the disk are available and both can mislead — check against the actual agent state, not the disk alone.
