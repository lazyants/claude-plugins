# Verifying teammate state: stale reads, report lag, duplicate agents

Three ways a shared-cwd team's on-disk/report state misleads if read carelessly: your OWN cached read goes stale, THEIR report lags THEIR disk, and a liveness misjudgment spawns a second agent onto one work-unit. All three share one discipline — verify against the live filesystem/transcript, never against a narrative or a memorized snapshot.

## Don't correct a teammate off a stale read

Verified 2026-07-08 (literary-translator assembler build, orphan_verse reviewer round). Teammates in a shared cwd edit the same files LIVE, so the disk moves between your reads. Read `assemble.py`, saw an "exemption" approach at a cached line, sent teammate B a fix message; re-read (still the stale snapshot — B was mid-edit) and fired a SECOND "SUPERSEDES — revert to the exemption" message. But B had ALREADY landed the *better* scan-based approach (the one codex round-2 then confirmed was gap-free). The superseding message was simply WRONG about what was on disk. B and D both had to stop and flag "your description doesn't match the file" — they were reading fresh each time; the lead was reacting to a cached mental model. It also told D to SKIP a boundary test that was actually correct for the real (scan) approach. Net: avoidable churn + teammates spending a round reconciling the lead's confusion instead of doing work.

**The rule: before sending a teammate a CORRECTION or a superseding instruction, RE-READ the current file.** A correction is higher-stakes than a first instruction — if it's wrong it creates conflicting messages the teammate must untangle, and can make them re-implement over already-correct work. The first instruction off a slightly-stale read is cheap to fix; a *superseding* one off a stale read is expensive.

**Trust fresh reads over your mental model.** The teammates' on-disk reports AND codex's read were all consistent with each other and with the disk; only the cached snapshot disagreed. When N independent fresh reads say X and your memory says Y, your memory is the stale one — re-read, don't argue from the snapshot.

**Convergence pattern that avoids the whole class:** don't react to mid-edit snapshots at all. A stream of diagnostics whose LINE NUMBERS keep shifting = someone is mid-edit; HOLD. Let every teammate report done + idle, THEN read the disk ONCE on the settled tree and run codex on it. Reserve mid-flight messages for genuinely new information, not corrections of a moving target.

**Standalone-verifier trick when you must verify an invariant that IMPORTS a mid-edit file.** 2026-07-09: the lead needed to confirm a SHA-1 region hash of `extract.py.template` after every teammate edit, but the canonical `selfcheck_region_hash` lives in `validate_extraction.py`, which ANOTHER teammate was concurrently editing (importing it mid-edit risks a syntax error / half-written state). Fix: INLINE the ~5-line algorithm into a standalone scratchpad script that imports nothing from the moving files (just reads the target's bytes and computes). Decouples verification from unrelated in-flight edits so the invariant can be checked any time without waiting for that teammate — trust-but-verify without a race. General rule: a verifier should depend only on what it's verifying, not on a sibling file that happens to hold the helper.

**Multi-generation / multi-session teams: a single-owner file changing under you is probably YOUR OWN teammate, not a hostile clobber — verify authorship BEFORE escalating to the user.** 2026-07-18 (plugins-migration build): named agents re-spawned came back suffixed `-2` (`orchestrator-2`, `unit-tester-2`) because the PRIOR (pre-compaction) generation still held the bare names and was alive. When `pm.py`'s mtime kept advancing with fix-shaped edits that hadn't been dispatched — plus a transient 11-test-fail + an undefined-symbol Pyright flash — this nearly triggered a "a parallel session is clobbering our data-safety file" alarm at the user. It was `orchestrator-2` (the lead's own re-spawn) resuming after a context reset, finding the PENDING-FIXES.md task list on disk, and applying exactly the fixes already staged (autonomous self-dispatch); the fails were mid-refactor snapshots. Diagnose before alarming:

1. `stat` the file twice across a delay — advancing mtime = a live editor.
2. Read the changed regions — edits matching your own staged list are your team, not hostile.
3. Attribute via the shared task-doc checkboxes + a direct `SendMessage` ("did you author the 23:05 edits?").
4. The `-2` name-collision is itself the tell a prior generation is alive.

Crying "hostile collision" wolf erodes trust as much as a real one; confirm it's your own team first, and only if it's genuinely a foreign session unreachable via `SendMessage` do you surface it to the user for arbitration.

**Corollary (reviewer freshness):** a reviewer dispatched against bytes that have since moved returns findings that are partly STALE (already fixed). Before dispatching fixes, verify each finding live-vs-stale against CURRENT source (grep the exact symbols); don't chase already-fixed findings or skip genuinely-live ones.

**The asymmetry is measurable, and it runs one way.** 2026-07-29 (enduser-handbook 1.12.0, five parallel teammates) produced four instances in one session: a teammate told their mutations "had not landed" when they had; a "banner is missing" correction contradicted by the lead's OWN gate run in the same turn; a grep for an exact phrase accusing a teammate of skipping a documentation note they had written in different words; and, worst, a stand-down-and-hand-over-your-files order sent to someone mid-flight who had already landed the exports being waited on. **Every time the teammate was right and the lead's read was stale; the reverse did not occur once.** Two consequences beyond the re-read rule above. First, the window that matters is *read-to-send*, not read-to-think: the reads were taken at the start of a turn and acted on at its end, comparing two different moments. Re-read immediately before the send, not when you start composing. Second, when a check contradicts a teammate's specific claim, **assume the check is wrong first** — and prefer searching for the substance over an exact phrase, because an over-precise needle produces a false accusation about someone else's work with no signal that it did.

**Reviewers and writers must not share a worktree — the lead's own dispatch is the usual cause.** Same session: a codex review and a `code-simplifier` were dispatched against the SAME snapshot worktree, and the simplifier edits. Codex rescued itself by reading committed bytes via `git show HEAD:<path>` and said so, but that was its judgement, not a guarantee. Separately, a teammate reported the shell gate flickering 709/709 → 708/709 and two transient unit failures, correctly traced to another teammate's in-progress edit in the shared tree. Give every review round its own DETACHED worktree at the reviewed commit that nothing writes to, and say so in the brief; a moving tree makes a verdict unattributable rather than merely noisy. (See also skill:parallel-work-partitioning for the pre-dispatch file partition this complements.)

**A backup of a teammate's uncommitted work is a stale read that OUTLIVES the moment — and it is trusted later, when they are gone.** Saving their in-flight tree as a `.patch` before a risky boundary (a restart, a rebase, a teardown) is right; treating that file as authoritative afterwards is not. It is a snapshot of a moving target with no staleness marker, and the danger point is exactly where suspicion is lowest: you are relieved to have a backup, the author is dead, and restoring feels like recovery rather than a write.

Measured 2026-07-30, same release: a patch saved while a teammate was still working captured an intermediate that the teammate then ABANDONED, and by restore time the live worktree held a different, finished fix instead. `diff` proved it — the two touched disjoint files (`capture-record.mjs` vs `capture-record.d.mts`). Restoring the patch would have reverted finished work that existed nowhere else and reinstated a discarded RED intermediate, all reported as a successful recovery.

Two rules. **`diff` the artifact against the live tree before restoring it, and when they disagree, BANK BOTH before choosing** — commit the live tree to a throwaway ref and keep the patch, then resolve which is later from evidence. Note what the measurement above does and does not establish: it proves *that* patch was stale, not that a live tree is newer whenever it differs. The boundaries that make you take a backup are the same ones that can move the tree BACKWARDS — a restart can drop uncommitted work, a rebase or a teardown-and-recreate can leave a tree rebuilt from an older commit — and in exactly those cases the patch is the only surviving copy, so an unconditional live-wins rule discards the thing the backup existed for. The live tree wins on evidence that it moved forward (it contains the patch's changes plus more, its files are newer than the capture, the author confirms), not on the bare fact of disagreement. With both banked, picking wrong is recoverable; that is the whole point of banking first. And **prefer a commit over a loose patch file**: a commit carries its parent and its timestamp, so a later reader can see what it was taken from, while a `.patch` in a directory is an undated claim about a tree that no longer exists. When the work is red and must not land on the branch, commit it to a throwaway ref rather than leaving it as a file.

This is the mirror image of report lag below: there the TEAMMATE's report lags their own disk edits; here it's the LEAD's read that's stale.

## Report lag: verify the round-specific NEW symbol, not the narrative

When driving multi-round fix work through named teammates (`builder`/`tester`), completion reports repeatedly lagged a **full round** behind their actual filesystem edits: each message confidently re-described the PREVIOUS round's deliverable while the CURRENT round's edit had already landed on disk (or was still landing). Twice this nearly led to re-dispatching already-done work.

**Two false-comfort traps, both defeated by the same check:**

- The report NARRATIVE may describe round N-1 even when round N was requested — don't trust it.
- Re-running the test suite stays GREEN across rounds (each round adds tests that pass), so "55 passed" does NOT prove round N's specific fix landed.

**How to apply:** after dispatching a round-N fix, verify the round-N deliverable by `grep`-ing the file for its round-SPECIFIC new symbol (the new constant / function / `except` clause / removed line) AND running the one targeted test — BEFORE either re-dispatching (avoids duplicate work) or banking it. The on-disk grep is what disambiguates; the report text and the suite pass-count do not. Edits reliably land FASTER than reports arrive, so a disk check a beat after dispatch usually already shows the change.

**Sharper form — re-run the FIX'S BEHAVIOR yourself, not the teammate's pasted repro.** A teammate's "before/after" paste can exercise the WRONG code path and still look green. Verified: a deep-nesting test at too-shallow depth (`"["*100000...` on CPython 3.14) PARSES fine and is caught by an unrelated structural check, never reaching the `RecursionError` branch it claims to test — the report + suite both stay green while the intended path is untested. So independently reproduce the fix's OUTPUT (exit code + the round-specific message) against your own input, especially when a test hinges on a threshold/size/depth parameter you (or the teammate) guessed.

**Silence: no report arrives at all** (2026-07-11, literary-translator 1.3.3 review loop). Several teammates went straight to `idle_notification` with zero completion-report text after finishing a dispatched fix — no narrative to distrust, just silence. Same fix applies: don't wait for a report that may never come, and don't re-ask the teammate — go straight to `git diff --stat`/`grep` for the round-specific symbol and run the tests yourself. This happened 3+ times in one session with genuinely-complete work every time, so silence alone is not a red flag — treat it identically to a report you don't fully trust.

**Report-only deliverables: idle-with-`[to main]` means already delivered** (2026-07-12, plugin-gap investigation). For REPORT-ONLY deliverables (investigation/audit/research — nothing lands on disk), the deliverable IS the message, and the idle notification reliably arrives WITHOUT it. 8/8 background teammates that session (7 investigators + 1 PR builder) went `idle_notification` with no deliverable text; ONE `SendMessage` nudge each ("reply via SendMessage to \"main\" with your FULL deliverable") retrieved the complete report every time, usually within a minute. A LATER idle notification carrying a `"summary":"[to main] …"` field means the deliverable WAS already sent — that one is just a confirmation, don't re-nudge. So: disk work → verify on disk (above); report-only work → first bare idle = nudge once, idle-with-`[to main]`-summary = already delivered. Also confirmed: outward actions (`gh issue create` / PR) by the teammate ARE real even when the report is stuck — verify via `gh pr list`/`git worktree list`, which can beat the report by minutes.

**Total silence, not even an idle notification: harvest from the subagent transcript, don't nudge and don't re-run** (2026-07-19, 29-issue audit fan-out). Five parallel audit agents completed at 12:55–12:57; no completion notification, no idle ping, nothing. Silence is indistinguishable from "still working" — telling the user "a few more minutes" continued for 23 minutes and was only checked because the user pushed twice ("долго ещё?", "точно не завалились?"). Two-step recovery:

- **Liveness first, but know what it does NOT tell you.** Two `stat`/`ls` snapshots ~20s apart prove the transcripts are not growing. That distinguishes "not progressing" from "working" — it does NOT distinguish DIED from FINISHED; a first read of a 23-minute-stale mtime as "stopped" was the wrong read. Read the LAST entry of the transcript: `stop_reason: end_turn` on an `assistant` record means it finished cleanly and the deliverable text is right there.
- **Harvest from the subagent transcript.** Final report = the last `type:"assistant"` message's text in `~/.claude*/projects/<cwd-slug>/<SESSION-id>/subagents/agent-a<name>-<hash>.jsonl`. Extract with a streaming parser (never read raw JSONL into context — files were 215–285 KB each). Strictly better than a `SendMessage` nudge: no round-trip, no risk of RESUMING a completed agent into redundant work. Path gotchas: the `subagents/` dir hangs off the **session** id, not the id used in scratchpad task paths; and it can live under a different profile dir (`.claude`) than the one currently running (`.claude-bm`) — so `find ~/.claude*/projects -name 'agent-a*<name>*' -mmin -60` instead of assuming either.

**Total silence can also mean the agent never replies AT ALL, distinct from an agent that finished and merely didn't notify — and this shape has its own reconciled rule below.** See **"A closing review leg's silence is neither a verdict nor a death"** further down this file: the short version is that unrecoverable report-only silence justifies doing the investigation yourself to stay unblocked, but never justifies merging or banking a clean result on that leg — a closing leg (security/simplifier) can still deliver, genuinely late, with a real finding.

**A content-grep completion watcher fires on PARTIAL mid-edit state** (2026-07-15/16, SSK index-fix). When arming a background watcher (an `until grep -q <marker>` loop) to detect a teammate's edit landing, grepping for a new symbol/constant/string fires on its FIRST appearance — often BEFORE the surrounding logic is wired: a constant defined but not yet referenced ("unaccessed"); a field present but not yet wired into its consumer list; a test-count of +1 when 3 tests were expected. Fired 3-4× in one session, each forcing a re-armed stricter watcher and a near-misread ("teammate mis-reported" when it was mid-edit). Fix: prefer a BEHAVIORAL watcher — run the actual check (does the targeted test PASS? does the function produce the expected OUTPUT on a probe input?) rather than grep-for-marker, which is robust to partial edits.

**A timely, honest test-failure report can be a false negative from CONCURRENT shared-worktree activity** (2026-07-17, literary-translator skeptic-pass build). Four teammates each ran the FULL suite at once in the shared worktree; one reported a `FileNotFoundError` flake in ANOTHER owner's test (a per-run tmp file) that PASSED standalone AND on re-run. Root cause was environmental — a test reading a sibling's file mid-rewrite / a pytest tmp-dir race under concurrent suites — NOT a bug, and not a mis-report either. Fix: before dispatching any fix for a teammate-reported failure observed during concurrent multi-teammate suite runs, the LEAD re-runs it SERIALLY (the file alone, then the full suite) — a green serial run rules out only a DETERMINISTIC branch defect (an INTERMITTENT branch defect and a concurrency artifact both remain open), so it leaves the CAUSE unestablished and the disposition it earns is "cause unknown; possibly an intermittent branch bug, possibly a concurrent writer", never "concurrency artifact, closed" and never "not a branch bug". Chasing it as a CONFIRMED real bug, OR blaming the teammate, is the miss. **Caveat on that serial re-run: a green does NOT establish "concurrency artifact" as the mechanism, and a failure that vanishes on retry is equally consistent with a teammate's live scoped mutation that has since been restored — see shared-worktree-run-validity.md, which also covers why a GREEN from a shared tree is just as unusable as a red.**

**Inverse trap: disk can lag an ALIVE teammate's in-progress work — don't re-dispatch off a clean `git status`** (2026-07-11, enduser-handbook #110 build). The `core` teammate was mid-build; running `git status` EARLY (before its first save landed — the edits arrived ~minutes later) showed the contract file unmodified with no completion report, which was read as "core is dead" — and in the SAME turn, both a status-check AND a fresh `impl` teammate to rebuild the same file went out. Both then edited the same file (`profile-version.mjs`) in the shared cwd. It resolved benignly (both targeted the same frozen contract; last-writer-wins left a coherent file), but it was luck, not design. The miss was procedural: **not WAITING for core's reply before re-dispatching.** Fix: when a teammate's work isn't on disk yet, MESSAGE it and WAIT for the answer (alive-but-mid-edit vs actually-dead) before spawning a replacement for the same file; a clean `git status` a beat after dispatch means "hasn't saved yet" at least as often as "died".

**A report that UNDER-claims is still a report — check the ARTIFACT, not the self-description** (2026-07-20, literary-translator 1.11.0). A teammate's chat summary said its file left a limitation uncovered "at all sites"; the FILE actually named the one uncovered site correctly and listed the three covered ones by test name. Firing a correction at the file based on the summary nearly rewrote prose that was already right; the teammate pushed back with line numbers instead of complying. Two lessons: (1) a working rule of "don't trust a report that claims SUCCESS" is incomplete — pessimistic/humble self-descriptions are not pre-verified either; the correct rule is *act on the artifact, never on the report*, in either direction. (2) An "uncovered everywhere" claim needs the same experiment as a "covered everywhere" claim.

## A closing review leg's silence is neither a verdict nor a death

Four measured incidents, all from the same week of `literary-translator` releases, look like they disagree about what to do when a closing review leg (a security pass, a `code-simplifier` pass, or similar) goes silent. They don't disagree — each caught a different piece of one reconciled rule, and no single one of them is the whole story.

- **2026-08-18, ~90 minutes, four `SendMessage` pings, no answer ever** (`code-simplifier` + a security reviewer, one session). The `code-simplifier`'s work was still recoverable from disk (`git diff` showed exactly what it did); the security leg was report-only and left no trace. Lesson taken: a review leg with no artifact on disk cannot be evidenced by having spawned an agent for it — do the work yourself rather than wait indefinitely, and don't report the leg as having run. The direct-probe technique that replaced it: write a probe script OUTSIDE the repo tree, drive the real module via `importlib`, assert on real filesystem outcomes — took ~20 minutes and was more targeted than the brief anyway, because the edges of the new code were already known. (Hygiene corollary: a probe-writing agent may drop scratch files into the worktree — check `git status` before committing, and tell the agent explicitly to keep scratch files out of the tree.)
- **LT 1.31.0, PR #594, same day: the silent leg's finding arrived AFTER the merge and was the most valuable finding of the release.** The closing security agent never delivered before the merge went out; its delayed report carried a real MAJOR against a guard the release itself had just added (a mark-counting cap that counted marks as written instead of after NFD, which the shipped code's own comment claimed to prevent). The lesson recorded there, verbatim: *"A closing-leg agent that never reports is not a leg that found nothing... do not merge on a silent closing leg — re-dispatch or wait."*
- **LT 1.33.1, PR #603, same day: both closing legs eventually delivered — ~25 minutes and three resend requests each.** Security came back CLEAN, the simplifier found 1 MINOR + 1 NIT, both reproduced before applying. Their late arrival made an earlier user-facing "they went silent" statement stale — a claim that should not have been made while the legs were still only slow, not dead. Lesson: **a slow leg is not a dead one**, and ~25 minutes with a few resends is a measured normal for this class of leg, not a stall.
- **LT 1.34.0, PR #602: the closing-pass agents delivered ~2 hours after going idle, and by then the MAJOR they found was already fixed.** Both `simplifier` and `security` went silent; both legs were run directly in the meantime; their reports then arrived pinned to the pre-fix SHA — one MAJOR (model-written strings forging a heading) was already closed, 2 of 3 simplifier dead-code items were already gone. Lesson, verbatim: **verify a late report against CURRENT source before acting.**

**The reconciliation these four support:**

1. **Silence is not a verdict.** Never bank a clean result, and never merge, on a leg that has not actually reported — the 1.31.0 incident is direct proof a silent leg can still be sitting on the release's most important finding.
2. **Silence is also not death.** ~25 minutes and three resends (1.33.1) is a measured normal for a closing review leg, not a stall — the one-ping-then-redispatch-unnamed timeline in the Message discipline section of SKILL.md is calibrated for a fast, chatty single-shot teammate, and does not transfer to this class of leg without producing false "they went silent" statements like the one 1.33.1 had to walk back.
3. **So do the work yourself to unblock — but that does not retire the leg.** Doing your own direct investigation (the probe-script technique above) is legitimate for staying unblocked when a report-only leg's silence has already run past a normal wait; it is not a substitute verdict for that leg, and it does not entitle you to bank the leg as clean or as run. What actually has to wait is the MERGE (or any "clean" verdict written down as fact) — not your own forward progress. The 1.31.0 and 1.34.0 incidents both ran the legs directly to keep moving and both still got a real, late, independent report afterward — in one case adding a finding, in the other confirming most of it was already moot. Neither outcome was knowable in advance, which is exactly why the leg has to be allowed to keep landing rather than written off.
4. **A late report is about the SHA it read, not about current source.** Once a report from a closing leg arrives after you have moved the tree — fixed something, merged, rebased — re-verify every finding in it against CURRENT source before acting on any of it (1.34.0). Some findings will already be closed; treating the report as still describing the live tree either wastes a round re-fixing something already fixed, or — the 1.31.0 direction — lets a finding that is NOT stale slip past because the report as a whole "looked late and probably moot."

## A status field can hide a partial fan-out application

A schema with `status: applied | refused | already-true` has no value for "did three of five parts", so an owner that ships the prose half of a row and declines its code half reports **`applied`**. The aggregate then reads "23 applied, 0 refused" and the release headline inherits a completeness claim nothing checked. Measured: one row shipped 3 of 5 parts, another 1 of 2, both reported `applied`; a reviewer found them only by re-reading the rows' own Edit lines against the tree.

**The owners were not being dishonest** — one wrote a detailed refusal rationale in its free-text `what_changed` field, where nothing aggregates it. The defect is the schema and the aggregation, not the reporter.

Two fixes, both cheap: give the status enum a `partial` value **and** require a per-part checklist when a row's Edit line names more than one site; then aggregate on the checklist, never on the status field. And re-derive the headline count from the parts, not from the owner reports — "N applied, 0 refused" is a measured claim about the deliverable, and it is exactly the kind of number that is first into the release notes and last to be checked.

## Duplicate agents on one work-unit in a shared cwd

Two agents ending up on the same work-unit in one shared cwd arises two ways; both produce the same hazard — two agents owning the same files, which is exactly how an unaccounted-for / half-clobbering edit lands. Contained both times only because the duplicates happened to verify rather than clobber — do not rely on that luck.

**Trigger 1 — reusing a still-ALIVE name (silent twin).** Verified 2026-07-20 (literary-translator 1.11.0). Dispatching a new round under the SAME names as the previous round (`A2c`, `A3b`) without realising those agents were still alive and idle: the harness did not error or reuse them — it created **`A2c-2`** / **`A3b-2`**, and both generations then existed at once. The OLD `A2c` truthfully reported it had touched nothing (true — the edits were the new twin's), and the escalation read as *an unowned agent editing production files*. Nothing was wrong, but that is indistinguishable at first glance from a real rogue edit. Message names resolve to the LATEST holder, so addressing `A2c` after `A2c-2` exists may not reach whom is meant.

**Trigger 2 — re-dispatching after wrongly concluding a mid-flight agent DIED.** Verified 2026-07-24 (enduser-handbook 1.10.0, #223). After a `/compact`, checking the worktree and seeing `git status` CLEAN led to concluding the compaction had killed the Phase-1 agents and their work was lost — so the same work was re-dispatched under FRESH names (`EH-CORE-b`, `EH-DOC-b`). The originals were actually **alive and mid-flight**; the clean-disk check was a snapshot taken before they had flushed. Minutes later the originals reported complete → two agents (different names) had been racing on the same files. The `-b` duplicates wisely verified-not-rewrote, so nothing was clobbered, but a concurrent write race on the same module could have produced a half-merged file.

**Trigger 3 — the liveness PROBE is itself a resurrection event, so check-then-re-dispatch in one turn is a race by construction.** Verified 2026-07-26 (enduser-handbook 1.11.0). A named teammate went **two hours** with zero edits on disk and no answer to a status ping — far past the short flush windows above, and about as close to proof of death as this evidence ever gets. The work was re-dispatched to a fresh agent. The ping then woke the original, which resumed editing the very files the replacement now owned. Both adapter documents were being written while the new agent was investigating; it caught the collision only by noticing an mtime **30 seconds old** on a file its brief called clean, and stopped before writing. So the length of the stall is not the variable — *a stalled agent is dormant, not dead, and your probe is what ends the dormancy.* Send the probe and WAIT for the answer as a separate step; never in the same turn as the replacement dispatch.

**A clean working tree mid-run is a snapshot, not proof of loss.** After a compaction/interruption, do NOT infer a dispatched background agent is dead from a clean (or empty) tree — a live agent that hasn't written yet looks identical to a dead one.

**How to apply:**

- Use a FRESH name per round (`A2c` → `A2d`), and **stand down** agents you are done with rather than leaving them idle-but-live (still named, still addressable).
- **Before RE-dispatching work thought to be lost, verify the original is actually dead/done — not that the disk merely looks empty.** Wait for its report, or check liveness (a live agent will still message/idle-notify); a clean tree alone settles nothing. Re-dispatch only after confirming.
- **If a duplicate is discovered running: FREEZE first** (message both to stop, do not write), then verify on-disk COHERENCE (syntax + full suite, not just presence) to tell a clean single-author result from a half-clobbered one, then commit the verified-good state as a restore point, then stand the duplicates down. An uncommitted good state is MORE vulnerable to a late clobber than a committed one.
- **Committing the blend is only right when the work is COMPLETE and verifiable. When the duplicate's edits are partial and no check was ever run on them, preserve them as a patch file and `git checkout --` back to the last commit instead** — then hand the patch to the single surviving owner as a *reference draft*, explicitly not a base. A half-applied edit whose provenance you are guessing at cannot be verified, only re-derived, and starting the survivor from a known commit is what makes its later report checkable. Sample the mtimes until they hold steady BEFORE resetting: in the 2026-07-26 case the file was written once more *after* the freeze message and *after* the patch snapshot, so resetting on the first quiet reading would have preserved a state that no longer existed and discarded the real one.
- A truthful "I haven't touched that" does not mean nobody has; a clean tree does not mean the agent is dead. Both readings of the disk are available and both can mislead — check against the actual agent state, not the disk alone.

## Resolving which name a SendMessage reaches

`SendMessage` addresses a peer only by the **name** `ListAgents` prints (plus its ` [ref]` suffix when the bare name is refused). It does not accept a session UUID. So when two peers sit in the SAME project — e.g. two book-translation sessions sharing one cwd — the name alone does not say which peer is which, and sending to the wrong one can mean a write to the wrong live dataset.

**The mapping is on disk:** `~/.claude/sessions/<pid>.json` — one file per live session, holding `name`, `sessionId`, `cwd`, `status`, `pid`. Filter by `cwd` and read `name` ↔ `sessionId`. It is shared across profiles (`~/.claude2/sessions` is a symlink to `~/.claude/sessions`), so one glob covers every profile. *(Re-verified 2026-08-22 with `ls -ld`: `~/.claude2/sessions` is indeed a symlink to `~/.claude/sessions`, not a separately-written mirror. Reading the same file through four profile paths looks exactly like four synchronised copies, so a content comparison across profiles cannot tell the two apart — `ls -ld` can, and is the check to run before assuming an edit does or does not propagate.)*

**The trigger, because knowing the registry exists did not make it fire.** With two same-cwd peers, inferring the mapping from **reply order** (assuming the first responder was the one `ListAgents` had shown as `busy`) sent each session the OTHER's answer. Both caught it, from content that could not be theirs. Nothing was written to a live root, but both peers spent a round refuting a state that was not theirs.

So the rule is not "the registry exists", it is: **before the FIRST SendMessage that carries project-specific content to a same-cwd peer, resolve name→sessionId→project from the registry.** Reply order, `busy`/`idle` status, and start time are all inferences that look like evidence. The tell that you are about to make this mistake: you can name which peer is which but cannot name the file you read it from.

Corollary worth keeping: a peer given the wrong project's state is a GOOD detector — it refutes from data it does not have. Route the correction back to both, and separately check whether the mix-up reached the user's own summary, which is the copy that actually matters and may well be clean.

**Two things that do NOT work for figuring out who a peer is, both tried:**

- **Asking the session its own name, in prose.** A session does not know it — asked directly, it answers that Claude Code assigns no session name, only ids (`sessionId`, `session_01…`, the profile, the path-mangled project name). A probe worded "what is your name" cannot resolve anything this way.
- **Grepping the transcripts for the peer name.** Both transcripts named a THIRD session that no longer existed, and neither contained its own name — a result that reads like an answer and is not.

**What DOES work for a session identifying ITSELF (as opposed to a prose question):** matching your own `sessionId` against the registry files directly — e.g. to establish "am I the only live session in this cwd", grep `~/.claude*/sessions/*.json` for your own `sessionId` rather than asking in words. *(Confirmed 2026-08-22: this is how a session established it was the only live one in its project.)* This is a different mechanism from the two that fail above — it reads the registry, it does not ask the session to self-report — so it is not a counterexample to either "does not work" case, just a third technique the earlier note didn't test.

A probe still works if worded as "which dataset/root are you on" (not "what is your name") — the reply arrives wrapped as `<cross-session-message from="…">` and the harness stamps the sender's name on it, so the peer never has to know its own name. But the registry answers it read-only, with no message injected into a session that may be mid-write.

## A peer session's silence is its turn having ended, not a subagent stall

This is different from a spawned subagent, and the difference decides what to do. A peer Claude session (`SendMessage` over a socket, e.g. `ListAgents`-discovered cross-session peers, not `Agent(name=…)`-spawned teammates) runs turn by turn: it finishes, reports, and **stops until someone sends it a message.** Its silence carries no information about being stuck, and no amount of watching will end it.

Measured 2026-08-13: a peer went quiet for 65 minutes after a commit. This was read as it being stuck at a permission prompt "blocking its whole turn," and reported to the user as such. Wrong on both counts — the denial had returned instantly as an ordinary error, blocking one command and nothing else; the peer had finished its parcel, committed, reported, and ended its turn. It was idle *between* turns. The follow-up message is what restarted it.

**How to apply.** Treat a peer as something you DRIVE, not something you monitor. If a peer has outstanding work and goes quiet, the correct action is to send it a message — not to diagnose why it stopped, and above all not to report a diagnosis of the stall to the user. Say "it has not reported since X" (observed) rather than "it is stuck on Y" (inferred). And when a peer says "starting now" and then goes silent, that is the ordinary shape of a turn ending, not evidence that the work began.

Corollary for monitoring: a session doing hand edits or reading produces no journal writes and no processes, so every automatic signal reads it as stopped. Silence-based watchdogs on a peer are noise generators; the only reliable status is to ask the source directly, never to build a proxy for it.
