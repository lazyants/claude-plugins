# Review-loop discipline

Procedural know-how for the iterative fix → code-simplifier → codex → security-review loop: how to shape a fix so the next round doesn't re-find it, how to tell a converging loop from a thrashing one, how to prove the fix is actually right, and how to keep scope from ballooning. These are deliberate techniques for during the loop — the always-on reflexes (red-before-green, run all three reviewers) live elsewhere.

Two through-lines run under everything below. **Close the CLASS, not the instance:** when a reviewer keeps returning new cases with the same root cause, stop patching locations, enumerate the whole set, and state the invariant so the reviewer verifies the class is closed. **Know when to stop:** a loop that keeps DELETING complexity and shifting findings from architectural to wording is converging; one adding normalization layers to chase an ambiguous or impossible property is not — exit deliberately, don't wait for the reviewer to say CLEAN forever.

Read the reference for the situation you're in:

- **references/converge-and-exit.md** — running the loop itself: healthy-vs-rabbit-hole signals, why finding-COUNT isn't the health metric, the deletion pivot, A/B finding classification, fencing ratified decisions, the stop criterion for a verifier/gate loop, the loop's exit condition, why review rounds are non-monotonic (a round-N optimization ask can be round-N+1's defect) and sometimes non-convergent (mutually-exclusive asks — pick the strictly-safer option, document the residual, escalate to the user instead of looping a 4th time), porting the diminishing-returns check to plan-review, and this project's codex-only review policy (no parallel Workflow review by default). Read when deciding whether to keep looping or how to end one.
- **references/close-the-class.md** — same-class whack-a-mole → enumerate + state the invariant; serialization/format migrations across every consumer; the completeness-GREP gate (and how to verify the gate itself isn't a no-op); algorithm-internal dedup and core-data-structure swaps; symbolic vs line-number refs. Read when the reviewer keeps finding new instances of one root cause.
- **references/inexpressible-defects.md** — when a defect class keeps recurring at new sites (or in the very check written to catch it): the four-rung escalation ladder from patching a site to making the defect structurally impossible to express, deleting the alternative path, denylist→allowlist for a checker, the symmetric-twin tell, reading a materialized artifact instead of reconstructing it, and how to brief a teammate with the design question plus explicit permission to refuse. Read at the 3rd occurrence of one class, not the 8th — and read it once more at AUTHORING time when writing or revising a normative doc that instructs a model to make calls (a SKILL.md, a runbook, an agent brief): that doc is a production caller, its drift from the real signatures is invisible to every runtime test, and the gate for it has to exist before the first defect rather than after the third.
- **references/fix-adds-review-surface.md** — a fix that ADDS a validation layer / gate / guarantee spawns its own review surface; new pipeline scripts must satisfy the pipeline's other invariants; guarantee-words and architecturally-impossible guarantees. Read when your fix introduces new machinery rather than changing a line.
- **references/net-negative-fixes.md** — comparing the fix's own worst failure to the bug's, erring toward the visible/recoverable direction, escalating a fundamentally-ambiguous tradeoff instead of whack-a-mole. Read when about to fix a reviewer's edge-case flag with a new gate/heuristic on an unreliable signal.
- **references/verify-the-fix.md** — verifying the fix covers the DOMAIN not just the ticket example, that a rebuild didn't regress or prove the wrong axis, checking that a probe or fixture DISCRIMINATES by running it against the pre-fix and post-fix commits (necessary, and conclusive in neither direction: an identical verdict cannot separate a mis-keyed probe from a failed fix, and a changed one only separates two TREES — attribution needs reachability evidence or a delta isolating the fix), source-completeness before trusting a rebuild, cross-checking your own artifacts, reproducing the gate's clean env, why an authoritative/reviewer-prescribed fix is not a review exemption (attack the data structure it discards, not just its intent), and why a bare `assert` guard vanishes under `python -O`. Read before saying "done" or "ready".
- **references/scope-gating.md** — gating a heavy optional component out FIRST, the mid-loop descope tell, the attestation-downgrade valve, and escalating an emergent scope balloon by tiers. Read when a plan/fix bundles a discretionary component or its scope grows past the issue.
