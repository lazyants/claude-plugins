## The adapter gap — `plain_text`/`custom` are documented but UNIMPLEMENTED

The shipped `assets/templates/extract.py.template` is the **gutenberg_epub** extractor and only that: `load_profile()` hard-`die()`s if `source.format != "gutenberg_epub"` (the format gate), `build()` unconditionally opens `source.path` as a ZIP/EPUB, and the two-phase hash hardcodes the gutenberg adapter config. Yet `references/source-format-adapters/plain-text.md` claims the same template gets its `# ADAPT-POINT:` sections "filled in for plain-text" — a docs↔executable MISMATCH. Trust the executable: there is no plain_text branch to adapt into.

Consequence: you CANNOT translate a `.txt`/OCR/scraped source through the shipped code. Fastest workaround = wrap the text as a **minimal EPUB** and run the proven `gutenberg_epub` adapter. The extractor's self-check region (`extract.py.template:1108–1277`) is genuinely GENERIC (grep confirms zero project literals), so a 0-footnote / 0-verse / 0-frontmatter Hebrew EPUB passes it. That region is hash-pinned by `validate_extraction.py`, so only the four `# ADAPT-POINT:` regions are editable.

## Get clean source text

Prefer `pdftotext -layout` on a PDF with a real text layer:
- Embedded Yiddish stays linear/correct under `-layout`; the **default mode reverses it** and `-raw` **fully reverses** it.
- Vocalized Hebrew comes out word-fragmented (intra-word spaces, e.g. `רב נו א מ ר`) in EVERY extractor including PyMuPDF — the model reconstructs it during translation (proven: an existing RU translation was made from the same fragmented dump). Do not try to de-fragment it yourself.
- Degraded per-line OCR dumps (garbled glyphs) are worse than `pdftotext` on a real text layer — prefer the text layer. Some source books ship only a finished translation and no clean original; there is nothing to extract from those.

### Extractor cleanliness is PER-PDF — measure garble, don't assume the default (SSK vol.2)

The `pdftotext`-preferred default above held for the Historiettes/Yiddish-era sources; it is NOT universal. A second Hebrew PDF (Siach Sarfei Kodesh vol.2) inverted it. Measured on pp22–214 of that PDF with the strong predicate below, `pdftotext -layout` gives **54.29% single-letter Hebrew tokens** — every letter cut off by an inserted U+0020 SPACE (`ַרבֵּ נּו אָ מַ ר`) — while **PyMuPDF `get_text("text")`** over the same page range gives **1.54% single-letter (clean)**, a 35× gap on one predicate. Both figures are post-bidi-strip (U+200E–200F, U+202A–202E); raw `pdftotext -layout` reads 49.41%, i.e. stripping the controls makes `pdftotext` look WORSE, not better — mechanism in the bidi bullet below. EVERY `pdftotext` mode is garbled on this PDF (default 54.29%, `-layout` 54.29%, `-raw` 25.93%); only PyMuPDF is clean. So pick the extractor by MEASUREMENT, per PDF:

- **Cheap garble detector — the single-letter-Hebrew-token ratio.** `clean ≈ 1.5–2.9%`, `garble ≈ 26–61%` (with the strong predicate below). **Read the two bands as what they actually bracket, not as tight predictions.** Clean = three clean artifacts × the three strong variants, spanning 1.54–2.93%; garbled = every garbled reading taken on this PDF, spanning 25.93% (`pdftotext -raw`) to 60.87% (the degraded manifest, whose own three variants sit at 54.30–60.87%). The per-artifact figures are listed under the code block so you can tell which measurement each band edge came from. The gap between the bands is ~9× and EMPTY, which is what makes the detector work; the decision threshold is the 5% gate below, not either band edge, so a new corpus landing at 8% or 30% is garbled just the same. The weak `len(token)==1` form reports that same degraded manifest as 13.7%. Run it on the extractor output AND on any prior run's EPUB you're tempted to reuse. NEVER reuse a previous project's EPUB without this check: the SSK July first-run EPUB was a 54%-garbled `pdftotext` dump, and slicing it would have carried the garble straight into a "clean" re-run.
  - **The check applies to ANY already-extracted corpus you are about to build on — including an existing `manifest.json` that already passed W2.** `validate_extraction.py` checks structure and conservation, NOT token integrity, so a green W2 gate is **not** evidence of clean text. Measure the manifest's own `plain_text`, not just a fresh extractor run. (Cost of skipping it: a full 40-segment LLM name canon — discovery, map-reduce consolidation, six verification rounds, two scope purges — was built on a manifest later measured at **54% single-letter** — fully garbled, not marginal — before anyone checked it.)
  - **COUNT HEBREW LETTERS INSIDE THE TOKEN, NOT `len(token)` — the weak predicate under-reports by ~4×.** A vocalized single letter (`אַ` = letter + combining mark) has ONE Hebrew letter but Python length 2, so `len(t) == 1` misses most shredded tokens. Use the strong predicate below, and count a token as a shredded FRAGMENT only if it holds exactly one Hebrew letter AND consists of Hebrew letters and marks alone — that keeps a structural siman marker (letter + hyphen) in the DENOMINATOR, where it belongs, without inflating the numerator:
    ```python
    import unicodedata

    def is_heb_letter(c): return "א" <= c <= "ת"
    def is_heb_mark(c):   return "֑" <= c <= "ׇ" and unicodedata.category(c) == "Mn"
    # denominator: every Hebrew-BEARING token (a siman marker is Hebrew text too)
    heb = [t for t in text.split() if any(is_heb_letter(c) for c in t)]
    # numerator: shredded FRAGMENTS only — exactly one Hebrew letter, and nothing
    # in the token but Hebrew letters and marks (so `ב-` is structure, not a fragment)
    single = sum(
        1 for t in heb
        if sum(1 for c in t if is_heb_letter(c)) == 1
        and all(is_heb_letter(c) or is_heb_mark(c) for c in t)
    )
    # second signal, over the RAW text (not the token list) so a mark after a
    # newline or punctuation is seen; a mark at index 0 is detached by definition
    detached = sum(
        1 for i, c in enumerate(text)
        if is_heb_mark(c)
        and (i == 0 or not (is_heb_letter(text[i - 1]) or is_heb_mark(text[i - 1])))
    )
    ```
    This matters for the interpretation, not just the number: the SSK degraded manifest measured **13.7% under `len(t)==1` but 54.30% under the strong predicate above** — i.e. it was in the *garble* band all along, and an earlier revision of this rule wrongly concluded from the weak figure that "the bands are not bimodal, an intermediate ~14% is still degraded". **With the strong predicate the bands ARE bimodal.** The bimodality is also robust to WHICH strong variant you pick, which is the reassuring part — measured on the real manifests (degraded / clean): excluding mixed tokens from the numerator only, as the code above does, **54.30% / 1.89%**; counting mixed tokens in the numerator, as an earlier revision of this doc published, **59.34% / 2.68%**; excluding them from numerator AND denominator **60.87% / 2.50%** — a **22×–29× clean/garble gap in all three**, with nothing in between. **That 22×–29× is the narrowest and most tightly scoped of the three "gap" figures in this section, and the only one holding the artifacts fixed:** it compares ONE degraded manifest against ONE clean manifest, variant by matched variant. It is not the ~9× band separation quoted with the bands above (worst clean vs mildest garbled, across every artifact and extractor — necessarily smaller, since it pairs the two nearest edges from DIFFERENT artifacts), and not the 35× at the top of this section (one extractor pair, one variant). Three different quantities, all correct; quote whichever you mean by name. **Name the artifact behind every one of these figures, because they were NOT all measured at the same pipeline stage.** That degraded/clean pair is `ssk-vol2-en-run/manifest.json` (degraded, 111,206 Hebrew tokens) against `ssk-w5-smoke/manifest.json` (clean, but only 1,269 tokens). The clean side then reproduces on two much larger artifacts at two other stages, each triplet in the SAME variant order as above (numerator-excluded, as the code runs / numerator-counted / excluded from both): the frozen pre-EPUB PyMuPDF dump `ssk-vol2-rerun-evidence/body.pymupdf.txt` (46,363 tokens) reads **1.54 / 2.93 / 2.02%**, and `ssk-vol2-slice-run/manifest.json` (13,944) reads **1.57 / 2.07 / 2.02%**. So the `1.5–2.9%` clean band brackets three artifacts × three variants spanning the extraction dump, a slice manifest and a smoke manifest — no clean artifact anywhere reaches 3%, and no variant of the degraded manifest drops below 54%. A number quoted without its artifact AND stage is the defect this section keeps re-growing: an unsourced "~4% clean" sat here for two revisions and fell outside its own clean band, and the artifact it named turned out to measure 1.54%. Only the WEAK `len(t)==1` predicate misleads: it reports that same degraded manifest as **13.7%**, manufacturing a middle band that does not exist. The general "suspect the predicate before inventing a band" rule → `skill:review-loop-discipline` → `references/verify-the-fix.md`.
  - **Pair it with a second signal — the `detached` counter computed above.** It counts combining marks whose predecessor is **neither a Hebrew letter nor another Hebrew mark** — not merely those following a space, which misses marks after a newline or punctuation. Measured by EXECUTING the block above against both manifests: **1 per 40.9 Hebrew tokens clean vs 1 per 10.9 degraded**. Read the clean side as a soft estimate — it rests on 31 detached marks over 1,269 Hebrew tokens, a small sample; the degraded side (10,217 marks over 111,206 tokens) is solid. The two larger clean artifacts named above put the clean rate well above what that small sample suggested — **1 per 28.3** (492 marks / 13,944 tokens, slice manifest) and **1 per 26.2** (1,772 / 46,363, PyMuPDF dump). Budget the gate against ~1 per 26, NOT 1 per 41: real clean text clears the ≤5% (1-per-20) threshold by only ~1.3×. **Compare the two gates' headroom under ONE stated rule, or the comparison is meaningless — worst clean reading across all three clean artifacts, measured with the predicate the gate ACTUALLY RUNS (the code above: mixed excluded from the numerator).** On that rule the single-letter gate's worst clean reading is 1.89% → **2.6× headroom**, and the detached gate's is 3.82% → **1.3×**. So detached is the likelier of the two to false-RED on clean text, with roughly half the margin. Note the rule needs no small-sample discounting to be fair: including the 1,269-token smoke manifest makes the single-letter side look WORSE (1.89% is its highest clean reading) while the detached worst comes from the 46,363-token dump either way, so neither gate is flattered by its own best sample. The ordering is not an artifact of the rule either — take instead the worst reading across ALL THREE predicate variants and single-letter still sits at 1.7× (2.93%, the purity-blind variant) against detached's 1.3×. What is NOT legitimate is mixing the two rules, one per gate. The space-only variant is a strict SUBSET of this predicate (a whitespace predecessor is necessarily neither letter nor mark), so it can only ever UNDER-count: re-measured, it misses 46 of the 10,217 degraded marks and 1 of the 31 clean, giving 1-per-10.9 and 1-per-42.3. Same verdict on this corpus, then — prefer the full predicate because it structurally cannot miss a mark after a newline or punctuation, NOT because it changed the answer here.
  - **Both gates, as integer arithmetic over the two counters above.** `20*single <= len(heb)` and `20*detached <= len(heb)` (≤5% each), asserting `len(heb) > 0` first. Both reuse the predicate CODE above — that is what keeps them in step with the measured bands. **Keep them as integer arithmetic:** a prose rate ("no more than 1 per 20 tokens") inverts easily, and that exact phrasing once shipped a gate that *failed* clean text and *passed* degraded. Full argument, and why the vectors below are not optional → `skill:review-loop-discipline` → `references/verify-the-fix.md`, "A measured threshold and its gate must share ONE predicate, as code". The Hebrew-specific vectors to pin: vocalized `אַ` (one Hebrew letter, and letters+marks only → IS a single-letter hit), `ב-` (IS in `heb` — a siman marker is Hebrew text — but NOT a single-letter hit: the hyphen makes it structure, not a shredded fragment), mark-after-newline and mark-after-punctuation (both detached), mark-after-its-base-letter and mark-after-another-mark (neither detached), a mark at index 0 of the text (detached), and U+05BE MAQAF (inside the mark range but category `Pd`, so not a mark).
  - **Why this bites hardest when building a name canon, not a translation.** An LLM discovery pass reads *through* shredding and returns a perfectly plausible canon — correct entities, correct English, correct descriptions. What it cannot do is invent clean Hebrew: the **surface strings it captures carry the shredding**, and those strings become the `source_form` KEYS of the plugin's 1:1 `canon.json` dictionary. Shredded keys silently under-match clean text, so name matching, the occurrence index and backlinks all fail quietly. Worse, **every verification round that reads the same degraded source shares the blind spot and reports green** — a name the shredding hid was invisible to the reviewers too. So: measure BEFORE discovery. If you find out late, the English side of the canon (entities, canonical forms, homonym splits, scope rulings — the expensive judgments) is still reusable; only the Hebrew surfaces need re-deriving against clean text, plus a fresh gap check that the degraded pass could not have performed.
- **Strip bidi controls as HYGIENE, but do not expect the strip to rescue a garbled corpus — the EXTRACTOR choice is what moves the number.** An earlier revision of this bullet claimed the strip took this corpus "54%→4%"; executed, it does nothing of the kind. On this PDF PyMuPDF's `get_text("text")` output contains **zero** U+200E–202E controls — raw and stripped are byte-identical, so its 1.54% owes the strip nothing — while `pdftotext -layout` output carries **26,844** of them and stripping them moves the strong ratio the WRONG way, **49.41% → 54.29%**. The mechanism is the purity clause: a control inside a token makes it fail `all(is_heb_letter or is_heb_mark)`, so the fragment hides from the numerator until you strip it. The variant that ignores purity is unchanged by the strip in both directions (**59.34% either way**), which is the clean proof that the strip reveals fragments rather than repairing them. **Taken to its limit that purity clause is a false-GREEN hole, and THAT is the real reason to strip BEFORE measuring:** unstripped `pdftotext -raw` output (287,414 controls) scores **0.00% single-letter and PASSES the single-letter gate** — every fragment is impure, so the numerator empties — on a corpus that is total garbage. Only the `detached` gate rejects it, 99,063 detached marks against 68,243 Hebrew tokens. That is the two-gate design earning its keep; strip first and the same corpus reads 25.93% and fails both gates on its own. The controls sit at run and line boundaries, not between letters: the fragments in the example above are separated by U+0020 SPACES, and in the `-layout` output only 10,405 of its 65,992 single-Hebrew-letter tokens contain a control at all. So strip (controls are noise and they distort the purity test), then re-measure and switch EXTRACTOR if the ratio is still in the garble band. What REMAINS once a clean extractor is chosen is the genuine intra-word vocalization spacing the previous bullet describes — THAT residue the model reconstructs during translation; do not chase it. The distinction is load-bearing: whole-corpus letter-splitting is a fixable extraction artifact (choose the right extractor); intra-word vocalization spacing is not (leave it for the model).
- **Assert byte-identity to a frozen extraction dump.** Freeze the chosen clean extraction as `…/body.<extractor>.txt` and have the EPUB builder `raise SystemExit` unless its own re-extraction matches byte-for-byte — so the builder can never silently diverge from the evidence base the run is calibrated on. Do NOT "repair" (strip lines, drop blanks, join fragments); carry RTL tail word-fragments verbatim.
- **Siman markers split across two lines.** PyMuPDF breaks a `ב-<letters>` marker as a bare line OR as `ב-` on one line + the letters on the next; a full-line-only regex silently finds ~265 of 329 (~20% missed), with no error and no tell. Match BOTH forms, and cross-check the resulting marker count against an independent signal (e.g. the naive count) rather than trusting the first number — a derived count like this looks authoritative and is never questioned downstream. (Same class as the greedy-backbone fragility under Segmentation below.)
- **A garbled prior run's manifest — reuse the chapter-START markers, ignore its WORD COUNTS.** Garble ~doubles the token count, so any segment sizing computed on garbled text is wrong-sized — but every boundary still sits on a REAL, content-independent siman marker, and since garble only INFLATES counts, reusing garble-derived starts stays comfortably under `max_segment_words` on the clean text. So a prior (garbled) run's start markers are safe to reuse; its counts are not.

**No source-fidelity gate exists** — a splitter that drops or duplicates text passes W2 green. This is a real gap; you are the only check on completeness.

**Prove conservation at the CHARACTER level, body-only, to BE that check.** A token-level source-vs-EPUB diff FALSELY fails on two artifacts — split markers (`ב-`+`ג` as two source tokens vs the joined `ב-ג`) and `<title>` text leaking into extraction. Instead compare Hebrew-letters-only (`א`–`ת`), `<body>` only, between the source line-range and the built EPUB — it must be character-exact (54,579 == 54,579 for the SSK 12-chapter slice). Caveat: character conservation proves NO TEXT was lost, NOT that every siman boundary is right — a wrongly-dropped siman marker merges its body into the preceding section, conserving characters while losing a boundary (see the monotonic-filter warning under Structure attestation). So pair the character check with the source-attestation boundary gate; neither alone suffices.

## Normalization simulations over vocalized Hebrew must be mark-aware

When simulating a text-healing/normalization step (e.g. joining a letter to an adjacent ASCII
connector) over vocalized (pointed) Hebrew, a check for "a Hebrew letter adjacent to the ASCII
connector" silently under-fires: in pointed text a `Mn` (nonspacing-mark, niqqud) codepoint sits
BETWEEN the letter and the connector, so an adjacency check that doesn't skip `Mn` marks heals
almost nothing and can produce a false "the fix made things worse" result. Fix: skip over
`Mn`-category codepoints when checking adjacency. This kind of contradiction is caught only by
asking "why does this contradict an already-proven fact?" — always reconcile a new measurement
against a prior verified finding before reporting it, rather than trusting the new number at face
value.

## EPUB-wrap mechanics

Build a 4-file EPUB:
1. `mimetype` — STORED (uncompressed) and FIRST in the archive
2. `META-INF/container.xml`
3. `content.opf` — single spine
4. `content.xhtml`

Rules for `content.xhtml`:
- The FIRST `<body>` child MUST be `<h2>` (anything before the first `<h2>` is classified as frontmatter).
- One `<h2>` per chapter; one `<p>` per paragraph.
- NO verse or footnote markup.
- Headings in the uncased script only — a Latin heading becomes a cased name candidate and breaks `--no-names-confirmed`.
- Force body classification with `adapter_config.gutenberg_epub.spine_overrides: {"content.xhtml":"body"}` (the heuristic otherwise wants a footnote-anchor signal a plain doc lacks).

## Segmentation — marker-snapped, NOT per-page and NOT a full siman ledger

For a book of numbered sections (simanim) where raw extraction yields far more bare marker-lines than real sections (embedded other-volume markers, inline cross-refs, stray front-matter, dups, out-of-order), a full gematria backbone is fragile — a greedy build broke at siman 164. Robust rule: a chapter boundary = the next bare-marker line AFTER each ~2600-word mark → ~40 chapters, every one starting at a real marker (no mid-section or mid-name split), all < 6000 words.

## Structure attestation gate (siman lists)

The model HALLUCINATES STRUCTURE, not just prose — e.g. it emitted a `## ב-תרצח` heading for a section that appears in NO source block (a plausible in-range gematria number the source simply lacks). Therefore:
- Gate every model-produced heading against SOURCE ATTESTATION — the marker must lead an actual source block — never against "it falls in the chapter's gematria window." In-range plausibility ≠ existence.
- Build the authoritative per-chapter siman list from the EPUB `<h2>` gematria WINDOWS `[chapter_start, next_chapter_start)`, deduped by gematria. This excludes inline cross-refs in BOTH directions — a monotonic-only filter WRONGLY drops a real siman when a forward cross-ref inflates the running max.

## Parsing an EXISTING Gutenberg EPUB (structure reference)

The above is for WRAPPING a PDF/OCR/txt source. When the source instead IS a real Project Gutenberg EPUB and you parse it yourself (or need to understand what the shipped `gutenberg_epub` adapter's self-check expects), its internal layout has fixed traps. These are the conventions of an **ebookmaker-generated PG EPUB** (learned parsing a 3-volume «Historiettes» t3) — the `FNanchor_N`/`Footnote_N` IDs, the separate notes files, and the body/notes signals below are ebookmaker/source conventions, NOT guaranteed properties of *every* PG EPUB. So PROBE the source's actual convention before applying this recipe: a book with different footnote IDs or inline notes would silently misclassify real body as front/back. The shipped `classify_spine_item` hook documents the escape hatch — extend its heuristic-fallback branch, or add `adapter_config.gutenberg_epub.spine_overrides` entries in `profile.yml`, when a source uses a different convention. The reusable structural facts:

- **Files ≠ chapters.** The body is split into N mechanical HTML files (`…-h-0.htm.html` … `-N`) = pagination, NOT semantic units (one book: 19 files, ~75 novellas). Segment by content (headings), never by file count.
- **Spine + classify by CONTENT, not filename.** Reading order lives in `content.opf` `<itemref idref>` → `<item id href>`. Classify each spine file by content signals: **body** = section `<h2>` headings + `id="FNanchor_N"` anchors; **notes** = many `id="Footnote_N"` defs, no headings; **front/back** = wrapper/cover/table-of-contents (may carry a stray `<h2>` — don't let one heading misclassify it as body).
- **Footnotes: anchor↔definition bijection, defs collected separately.** Inline `<a id="FNanchor_N" href="…#Footnote_N">[N]</a>` in the body → definition `id="Footnote_N"` gathered in dedicated NOTES files (not inline). Validate by the ID SETS, NOT the counts — equal cardinality false-greens the exact breakage it should catch (anchors `{1,1}` vs defs `{1,2}` both count 2, while an anchor is duplicated and def 2 dangles). A true 1:1 needs the anchor-ID set `==` the def-ID set AND no ID repeated on either side. The shipped `fn_bijection` self-check tests `anchors == defs` (set identity, reporting `dangling_anchor`/`dangling_def` by set difference), never `len(...) == len(...)` — on a clean t3 both sets are 1..423 with empty differences.
- **Footnote definitions SPILL across notes-file boundaries.** A single footnote's def can start (its `id="Footnote_N"` `<p>`) at the end of notes file N and continue (extra `<p>`/verse, no anchor) at the top of file N+1. Group footnotes over the CONCATENATED stream of all notes files, keeping the "current footnote" alive across the boundary — reset-per-file drops the continuation (its leading orphan node has no anchor → lost).
- **Verse markup.** Classes `poetry-container` / `poetry` / `stanza` / `line`. Some verse is quoted INSIDE footnotes, so register poem nodes by the UNION of markers, with a fallback for bare `.poetry`/`.stanza`/`.line` not inside a container — else you miscount.
- **`get_text(" ")` (space separator) CORRUPTS text two ways.** BeautifulSoup inserts the separator between EVERY pair of string nodes, so (1) a word split by inline markup — `<b>C</b>ertes` (drop-cap/acrostic) — becomes `"C ertes"`, and (2) an inline anchor replaced by a sentinel — `word<a>[1]</a>.` → `"word ⟦FNREF_1⟧ ."` (spurious spaces before punctuation). Count-based checks pass while the text is silently wrong (false-green). Fix: a custom extractor that emits a separator ONLY at block-level tags (`p/div/br/h*/blockquote/li/tr…`) and concatenates inline nodes with none; use `tag.get_text()` (empty sep) for inline-only nodes like a verse `.line`.
- **Recon before building the parser.** A cheap structural probe (spine-classify + bijection count + per-file heading/anchor/def/verse/word counts) validates the parse model on real bytes and de-risks the extractor before you write it.
